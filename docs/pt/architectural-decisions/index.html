Decisões de Design Arquitetônico

Esta página explica o raciocínio por trás das principais escolhas tecnológicas e arquiteturais do PgArachne. Estas decisões foram tomadas para priorizar performance, segurança e produtividade do desenvolvedor, garantindo ao mesmo tempo uma alta compatibilidade com agentes de IA e modelos LLM modernos.

1. JSON-RPC 2.0 vs. REST

O PgArachne utiliza JSON-RPC 2.0 como seu protocolo de comunicação primário em vez do tradicional REST.

Por que JSON-RPC 2.0:

  • Endpoint Único: Toda a comunicação ocorre via POST /api/{banco_de_dados}. Não há necessidade de projetar estruturas de URL complexas ou debater a semântica dos verbos HTTP.
  • Chamadas Autocontidas: Cada requisição é um objeto JSON completo (método + parâmetros + id). Este formato é trivial de gerar e processar para LLMs e agentes de IA com alta confiabilidade.
  • Tratamento de Erros Padronizado: Códigos e mensagens de erro fazem parte da especificação, eliminando a necessidade de „inventar“ convenções de códigos de status HTTP para erros de negócio.
  • Loteamento (Batching): O protocolo suporta nativamente requisições em lote, permitindo múltiplas operações (ex: várias chamadas de função) em uma única viagem de ida e volta HTTP sem trabalho extra.
  • Descoberta (Discovery): O endpoint de capacidades fornece uma descrição completa da API em um formato que os agentes de IA podem consumir para entender as ferramentas disponíveis sem alucinações.

Por que não REST:

  • Complexidade para IA: A semântica REST (GET/POST/PATCH/DELETE + parâmetros de URL + corpo) está dispersa em vários lugares, tornando mais difícil para os agentes de IA construir chamadas de forma confiável.
  • Exposição do Esquema: O CRUD sobre tabelas (estilo PostgREST) muitas vezes expõe a estrutura interna do banco de dados diretamente via API. O PgArachne expõe funções deliberadamente, mantendo a lógica de negócio encapsulada em SQL.
  • Ausência de Padrões: O REST não oferece um padrão universal para operações em lote, envelopes de erro multiplataforma ou descoberta automatizada de API.

2. SSE (Server-Sent Events) vs. WebSockets

Para notificações em tempo real, o PgArachne implementa Server-Sent Events (SSE).

Por que SSE:

  • HTTP Puro: O SSE é HTTP padrão. Funciona através de proxies, balanceadores de carga e CDNs sem configurações especiais de „upgrade de protocolo“.
  • Suporte Nativo do Navegador: A API EventSource é integrada em todos os navegadores modernos e gerencia a reconexão automática sem necessidade de bibliotecas cliente.
  • Corresponde à Semântica do NOTIFY: O comando NOTIFY do PostgreSQL é unidirecional (servidor para cliente), o que se ajusta perfeitamente ao SSE.
  • Multiplexação: Sobre o HTTP/2, centenas de fluxos SSE podem compartilhar uma única conexão TCP, tornando-o extremamente eficiente.
  • Simplicidade Operacional: As conexões SSE aparecem como requisições HTTP normais em logs e ferramentas de monitoramento, facilitando o debug e o rate limiting.

Por que não WebSockets:

  • Bidirecionalidade Desnecessária: Como o cliente nunca precisa enviar dados de volta pelo canal de notificação, a complexidade do WebSockets não traz benefício.
  • Problemas de Conectividade: WebSockets são frequentemente bloqueados ou encerrados prematuramente por firewalls corporativos e alguns balanceadores de carga em nuvem.
  • Maior Sobrecarga: Adiciona complexidade ao protocolo (handshakes, frames de ping/pong) que não é necessária para o simples streaming de eventos.

3. Go vs. Alternativas

O PgArachne é escrito em Go para oferecer o melhor equilíbrio entre performance e simplicidade de implantação.

Por que Go:

  • Binários Estáticos: Compila em um único arquivo executável sem dependências externas. A implantação é tão simples quanto copiar o arquivo para o servidor.
  • Concorrência: As goroutines do Go tornam o gerenciamento de milhares de conexões SSE e de banco de dados simultâneas leve e direto.
  • Biblioteca Padrão Robusta: As bibliotecas integradas para HTTP, TLS e JSON são de nível de produção e não requerem „node_modules“ ou ambientes de execução externos.
  • Compilação Cruzada: Gera facilmente binários para Linux, macOS e Windows (amd64 e arm64) a partir de qualquer máquina de desenvolvimento.

Por que não Node.js, PHP ou Ruby:

  • Runtimes: Estas linguagens requerem a instalação de um ambiente de execução específico em cada máquina de destino.
  • Eficiência: O loop de thread única do Node.js ou o modelo processo-por-requisição do PHP são menos eficientes para manter milhares de conexões SSE inativas.
  • Consumo de Memória: O Go utiliza significativamente menos memória por conexão do que as linguagens de script.

Por que não Rust:

  • Velocidade de Desenvolvimento: Embora o Rust ofereça performance extrema, sua complexidade (borrow checker) retarda a iteração para uma ferramenta focada em I/O onde a performance do Go já é mais do que suficiente.

Por que não C / C++:

  • Segurança: O gerenciamento manual de memória adiciona riscos de segurança significativos (buffer overflows) sem ganho de performance relevante em uma aplicação de gateway.

4. Funções PostgreSQL como Superfície da API

O PgArachne expõe deliberadamente funções do banco de dados em vez de tabelas puras.

Por que funções:

  • Encapsulamento: A lógica de negócio reside junto com os dados no banco de dados — um único lugar para auditoria, versionamento e segurança.
  • Segurança Explícita: Através da API, apenas as funções às quais foram explicitamente concedidas permissões EXECUTE para um papel específico são acessíveis.
  • Abstração: Validação de entradas, campos calculados e operações complexas em várias tabelas ficam ocultos para o cliente, fornecendo uma interface limpa.

Por que não CRUD em nível de tabela:

  • Acoplamento Forte: Expor as tabelas diretamente vincula sua API ao esquema interno do banco de dados, dificultando refatorações sem quebrar as aplicações cliente.
  • Fragmentação de Regras de Negócio: A lógica acaba sendo dividida entre restrições de banco de dados e qualquer middleware usado para filtrar as requisições HTTP.
