Sicherheit & Authentifizierung

PgArachne verlässt sich vollständig auf das PostgreSQL-Berechtigungssystem. Es erfindet keine Access Control Lists (ACLs) neu. Alle Abfragen werden unter der spezifischen Datenbankrolle des authentifizierten Benutzers ausgeführt — entweder durch SET LOCAL ROLE (Methoden 1–3) oder durch eine direkte Verbindung als der jeweilige Benutzer (Methode 4).

1. Interaktives Login (JWT)

Benutzer authentifizieren sich über die Login-Funktion mit ihrem echten PostgreSQL-Benutzernamen und -Passwort. Bei Erfolg erhalten sie ein generisches JWT. Wenn dieses Token verwendet wird, wechselt PgArachne die aktive Rolle für die Dauer der Anfrage zu diesem Benutzer.

2. Service-Konten (API-Token)

Für automatisierte Systeme oder Skripte können Sie langlebige API-Token verwenden.

  • Token werden in der Tabelle pgarachne.api_tokens gespeichert.
  • Jedes Token ist einem bestimmten Datenbankbenutzer/-rolle zugeordnet.
  • Senden Sie das Token über den Header Authorization: Bearer <token>.

Das Erstellen von API‑Tokens erfordert pgarachne_admin. Verwenden Sie pgarachne.add_api_token(...) mit einer Rolle, die Mitglied von pgarachne_admin ist.

3. Externer Identity Provider (eigenes JWT)

Wenn Benutzer außerhalb von PgArachne authentifiziert werden (z. B. über einen externen Auth-Dienst), kann dieser Dienst JWTs ausstellen und direkt an PgArachne senden.

  • Header-Format: Authorization: Bearer <jwt>.
  • Signatur: nur HMAC (HS256/HS384/HS512) mit demselben JWT_SECRET, der in PgArachne konfiguriert ist.
  • Pflicht-Claims: db_role (String, nicht leer) und db_name (String, muss zu /api/:database passen).
  • Empfohlener Claim: exp (Unix-Timestamp) für das Ablaufdatum.

Minimales Payload-Beispiel:

{
  "db_role": "demo_user",
  "db_name": "my_database",
  "exp": 1767225600
}

Wichtig: asymmetrische JWT-Algorithmen (z. B. RS256/ES256) werden von der aktuellen Server-Implementierung nicht akzeptiert.

4. Direkte Datenbankzugangsdaten (Basic Auth)

PgArachne unterstützt HTTP Basic Authentication. Der PostgreSQL-Benutzername und das Passwort werden direkt im Standard-Authorization-Header übergeben:

Authorization: Basic <base64(benutzer:passwort)>

Mit curl lässt sich dies besonders einfach verwenden:

curl -u demo_user:passwort \
  -X POST http://localhost:8080/db/my_database/jsonrpc \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","method":"api.hello_world","params":{},"id":1}'

Wesentliche Unterschiede zu den Methoden 1–3:

  • Es ist kein GRANT demo_user TO pgarachne erforderlich.
  • PgArachne führt kein SET LOCAL ROLE aus — die Verbindung wird direkt als der angegebene Benutzer hergestellt.
  • Verbindungs-Pools sind benutzerspezifisch und haben eine Lebensdauer von 5 Minuten.
  • JWT bleibt optional und wird für diese Methode nicht benötigt.

Wann sollten Sie Direkte Zugangsdaten verwenden?

  • Entwicklung & lokales Testen: Kein Token-Management, sofort einsatzbereit.
  • Skripte & Automatisierung: Einfache Authentifizierung ohne vorherigen Login-Schritt.
  • Interne Dienste: Wenn Zugangsdaten bereits sicher verwaltet werden (z. B. über Vault oder Kubernetes Secrets).

Für Produktionsumgebungen mit externen Clients sind langlebige API-Token (Methode 2) die bevorzugte Wahl.

Kritische Konfiguration: Proxy-Privilegien (nur Methoden 1–3)

Da sich PgArachne bei den Methoden 1–3 als der in DB_USER definierte Benutzer (z. B. pgarachne) verbindet und die Identität zu anderen Benutzern wechselt, muss der Proxy-Benutzer Mitglied dieser Zielrollen sein.

Führen Sie dieses SQL für jeden Benutzer/jede Rolle aus, die sich anmelden muss:

-- Erlaube 'pgarachne' zu 'demo_user' zu wechseln
GRANT demo_user TO pgarachne;

Bei Methode 4 (Direkte Zugangsdaten) entfällt dieses GRANT vollständig, da PgArachne sich direkt als der jeweilige Benutzer verbindet.
