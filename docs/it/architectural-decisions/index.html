Decisioni di Progettazione Architetturale

Questa pagina spiega il ragionamento alla base delle principali scelte tecnologiche e architetturali in PgArachne. Queste decisioni sono state prese per dare priorità a prestazioni, sicurezza e produttività degli sviluppatori, garantendo al contempo un'elevata compatibilità con i moderni agenti AI e modelli LLM.

1. JSON-RPC 2.0 vs. REST

PgArachne utilizza JSON-RPC 2.0 come protocollo di comunicazione primario al posto del tradizionale REST.

Perché JSON-RPC 2.0:

  • Endpoint Singolo: Tutte le comunicazioni avvengono tramite POST /api/{database}. Non è necessario progettare strutture URL complesse o discutere sulla semantica dei verbi HTTP.
  • Chiamate Autocontenute: Ogni richiesta è un oggetto JSON completo (metodo + parametri + id). Questo formato è banale da generare e analizzare per gli LLM e gli agenti AI con un'elevata affidabilità.
  • Gestione degli Errori Standardizzata: I codici e i messaggi di errore fanno parte della specifica, eliminando la necessità di „inventare“ convenzioni per i codici di stato HTTP per gli errori di business.
  • Batching: Il protocollo supporta nativamente le richieste batch, consentendo più operazioni (ad esempio, diverse chiamate a funzioni) in un unico round-trip HTTP senza lavoro aggiuntivo.
  • Discovery: L'endpoint delle funzionalità fornisce una descrizione completa dell'API in un formato che gli agenti AI possono consumare per comprendere gli strumenti disponibili senza allucinazioni.

Perché non REST:

  • Complessità per l'AI: La semantica REST (GET/POST/PATCH/DELETE + parametri URL + corpo) è distribuita in più punti, rendendo più difficile per gli agenti AI costruire chiamate in modo affidabile.
  • Fuga dello Schema: Il CRUD sulle tabelle (stile PostgREST) spesso espone la struttura interna del database direttamente tramite l'API. PgArachne espone deliberatamente funzioni, mantenendo la logica di business incapsulata in SQL.
  • Mancanza di Standard: REST non offre uno standard universale per le operazioni batch, wrapper di errore multipiattaforma o la scoperta automatizzata delle API.

2. SSE (Server-Sent Events) vs. WebSockets

Per le notifiche in tempo reale, PgArachne implementa Server-Sent Events (SSE).

Perché SSE:

  • HTTP Puro: SSE è HTTP standard. Funziona attraverso proxy, bilanciatori di carico e CDN senza configurazioni speciali di „aggiornamento del protocollo“.
  • Supporto Nativo del Browser: L'API EventSource è integrata in tutti i browser moderni e gestisce la riconnessione automatica senza librerie client aggiuntive.
  • Corrisponde alla Semantica NOTIFY: Il comando NOTIFY di PostgreSQL è unidirezionale (da server a client), il che si adatta perfettamente a SSE.
  • Multiplexing: Su HTTP/2, centinaia di stream SSE possono condividere una singola connessione TCP, rendendolo estremamente efficiente.
  • Semplicità Operativa: Le connessioni SSE appaiono come normali richieste HTTP nei log e negli strumenti di monitoraggio, facilitando il debug e il rate limiting.

Perché non WebSockets:

  • Bidirezionalità non Necessaria: Poiché il client non deve mai inviare dati attraverso il canale di notifica, la complessità di WebSockets non offre alcun vantaggio.
  • Problemi di Connettività: I WebSockets sono spesso bloccati o chiusi prematuramente dai firewall aziendali e da alcuni bilanciatori di carico cloud.
  • Maggiore Overhead: Aggiunge complessità al protocollo (handshake, frame ping/pong) che non è necessaria per il semplice streaming di eventi.

3. Go vs. Alternative

PgArachne è scritto in Go per offrire il miglior equilibrio tra prestazioni e semplicità di distribuzione.

Perché Go:

  • Binari Statici: Viene compilato in un unico file eseguibile senza dipendenze esterne. La distribuzione è semplice come copiare il file sul server.
  • Concorrenza: Le goroutine di Go rendono la gestione di migliaia di connessioni SSE e database simultanee leggera e immediata.
  • Libreria Standard Robusta: Le librerie integrate per HTTP, TLS e JSON sono di livello produttivo e non richiedono „node_modules“ o ambienti di esecuzione esterni.
  • Cross-compilazione: Genera facilmente binari per Linux, macOS e Windows (amd64 e arm64) da qualsiasi macchina di sviluppo.

Perché non Node.js, PHP o Ruby:

  • Runtime: Questi linguaggi richiedono l'installazione di un ambiente di esecuzione specifico su ogni macchina di destinazione.
  • Efficienza: Il loop a thread singolo di Node.js o il modello processo-per-richiesta di PHP sono meno efficienti per mantenere migliaia di connessioni SSE inattive.
  • Impronta di Memoria: Go utilizza molta meno memoria per connessione rispetto ai linguaggi di scripting.

Perché non Rust:

  • Velocità di Sviluppo: Sebbene Rust offra prestazioni estreme, la sua complessità (borrow checker) rallenta l'iterazione per uno strumento orientato all'I/O dove le prestazioni di Go sono già più che sufficienti.

Perché non C / C++:

  • Sicurezza: La gestione manuale della memoria aggiunge rischi di sicurezza significativi (buffer overflow) senza un guadagno di prestazioni rilevante in un'applicazione gateway.

4. Funzioni PostgreSQL come Superficie API

PgArachne espone deliberatamente funzioni del database piuttosto che tabelle grezze.

Perché le funzioni:

  • Incapsulamento: La logica di business risiede insieme ai dati nel database — un unico punto per il controllo, il versionamento e la sicurezza.
  • Sicurezza Esplicita: Tramite l'API sono accessibili solo le funzioni a cui sono stati esplicitamente concessi i permessi EXECUTE per un ruolo specifico.
  • Astrazione: La validazione degli input, i campi calcolati e le operazioni complesse su più tabelle sono nascosti al client, fornendo un'interfaccia pulita.

Perché no CRUD a livello di tabella:

  • Accoppiamento Stretto: Esporre le tabelle direttamente lega la tua API allo schema interno del database, rendendo difficile il refactoring senza interrompere le applicazioni client.
  • Frammentazione delle Regole di Business: La logica finisce per essere divisa tra i vincoli del database e qualsiasi middleware utilizzato per filtrare le richieste HTTP.
