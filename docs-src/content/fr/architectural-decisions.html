Décisions de Conception Architecturale

Cette page explique le raisonnement derrière les choix technologiques et architecturaux clés de PgArachne. Ces décisions ont été prises pour donner la priorité aux performances, à la sécurité et à la productivité des développeurs, tout en assurant une haute compatibilité avec les agents d'IA et les modèles LLM modernes.

1. JSON-RPC 2.0 vs REST

PgArachne utilise JSON-RPC 2.0 comme protocole de communication principal au lieu du traditionnel REST.

Pourquoi JSON-RPC 2.0 :

  • Endpoint Unique : Toute la communication passe par POST /api/{base_de_donnees}. Il n'est pas nécessaire de concevoir des structures d'URL complexes ou de débattre de la sémantique des verbes HTTP.
  • Appels Auto-contenus : Chaque requête est un objet JSON complet (méthode + paramètres + id). Ce format est facile à générer et à analyser pour les LLM et les agents d'IA avec une grande fiabilité.
  • Gestion des Erreurs Standardisée : Les codes et messages d'erreur font partie de la spécification, éliminant ainsi le besoin d'inventer des conventions de codes d'état HTTP pour les erreurs métier.
  • Lotissement (Batching) : Le protocole prend nativement en charge les requêtes par lots, permettant plusieurs opérations (par exemple, plusieurs appels de fonctions) en un seul aller-retour HTTP sans travail supplémentaire.
  • Découverte (Discovery) : L'endpoint de capacités fournit une description complète de l'API dans un format que les agents d'IA peuvent consommer pour comprendre les outils disponibles sans hallucinations.

Pourquoi pas REST :

  • Complexité pour l'IA : La sémantique REST (GET/POST/PATCH/DELETE + paramètres d'URL + corps) est dispersée à plusieurs endroits, ce qui rend plus difficile pour les agents d'IA de construire des appels de manière fiable.
  • Fuite de Schéma : Le CRUD sur les tables (style PostgREST) laisse souvent filtrer la structure interne de la base de données directement via l'API. PgArachne expose délibérément des fonctions, gardant la logique métier encapsulée dans SQL.
  • Absence de Standards : REST n'offre pas de standard universel pour les opérations par lots, les enveloppes d'erreurs multiplateformes ou la découverte automatisée d'API.

2. SSE (Server-Sent Events) vs WebSockets

Pour les notifications en temps réel, PgArachne implémente les Server-Sent Events (SSE).

Pourquoi SSE :

  • HTTP Pur : SSE est du HTTP standard. Il fonctionne à travers les proxys, les équilibreurs de charge et les CDN sans configuration spéciale de „mise à niveau du protocole“.
  • Support Natif du Navigateur : L'API EventSource est intégrée dans tous les navigateurs modernes et gère la reconnexion automatique sans aucune bibliothèque cliente.
  • Correspond à la Sémantique NOTIFY : La commande NOTIFY de PostgreSQL est unidirectionnelle (serveur vers client), ce qui correspond parfaitement au SSE.
  • Multiplexage : Sur HTTP/2, des centaines de flux SSE peuvent partager une seule connexion TCP, ce qui le rend extrêmement efficace.
  • Simplicité Opérationnelle : Les connexions SSE apparaissent comme des requêtes HTTP normales dans les journaux et les outils de surveillance, facilitant le débogage et le filtrage (rate limiting).

Pourquoi pas WebSockets :

  • Bidirectionnalité Inutile : Comme le client n'a jamais besoin d'envoyer de données via le canal de notification, la complexité des WebSockets n'apporte aucun avantage.
  • Problèmes de Connectivité : Les WebSockets sont souvent bloqués ou fermés prématurément par les pare-feux d'entreprise et certains équilibreurs de charge cloud.
  • Surcharge Plus Élevée : Ajoute une complexité de protocole (handshakes, trames ping/pong) qui n'est pas nécessaire pour le simple streaming d'événements.

3. Go vs Alternatives

PgArachne est écrit en Go pour offrir le meilleur équilibre entre performances et simplicité de déploiement.

Pourquoi Go :

  • Binaires Statiques : Compile en un seul fichier exécutable sans dépendances externes. Le déploiement est aussi simple que de copier le fichier sur le serveur.
  • Concurrence : Les goroutines de Go rendent la gestion de milliers de connexions SSE et de base de données simultanées légère et simple.
  • Bibliothèque Standard Robuste : Les bibliothèques intégrées pour HTTP, TLS et JSON sont de qualité production et ne nécessitent pas de „node_modules“ ni d'environnements d'exécution externes.
  • Compilation Croisée : Cible facilement Linux, macOS et Windows (amd64 et arm64) depuis n'importe quelle machine de développement.

Pourquoi pas Node.js, PHP ou Ruby :

  • Runtimes : Ces langages nécessitent l'installation d'un environnement d'exécution spécifique sur chaque machine cible.
  • Efficacité : La boucle à thread unique de Node.js ou le modèle processus-par-requête de PHP sont moins efficaces pour maintenir des milliers de connexions SSE inactives.
  • Empreinte Mémoire : Go utilise beaucoup moins de mémoire par connexion que les langages de script.

Pourquoi pas Rust :

  • Vitesse de Développement : Bien que Rust offre des performances extrêmes, sa complexité (borrow checker) ralentit l'itération pour un outil axé sur l'I/O où les performances de Go sont déjà plus que suffisantes.

Pourquoi pas C / C++ :

  • Sécurité : La gestion manuelle de la mémoire ajoute des risques de sécurité importants (débordements de tampon) sans gain de performance significatif dans une application de passerelle.

4. Fonctions PostgreSQL comme Surface d'API

PgArachne expose délibérément des fonctions de base de données plutôt que des tables brutes.

Pourquoi les fonctions :

  • Encapsulation : La logique métier réside avec les données dans la base de données — un seul endroit pour auditer, versionner et sécuriser.
  • Sécurité Explicite : Seules les fonctions auxquelles ont été explicitement accordées les permissions EXECUTE pour un rôle spécifique sont accessibles via l'API.
  • Abstraction : La validation des entrées, les champs calculés et les opérations complexes sur plusieurs tables sont masqués pour le client, offrant une interface propre.

Pourquoi pas de CRUD au niveau des tables :

  • Couplage Fort : L'exposition directe des tables lie votre API à votre schéma de base de données interne, ce qui rend la refactorisation difficile sans casser les applications clientes.
  • Fragmentation des Règles Métier : La logique finit par être divisée entre les contraintes de la base de données et tout middleware utilisé pour filtrer les requêtes HTTP.
