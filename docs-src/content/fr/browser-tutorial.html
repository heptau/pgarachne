Tutoriel pas à pas pour le navigateur

La configuration fonctionnelle la plus simple possible : une base de données PostgreSQL, PgArachne et une seule page HTML ordinaire qui se connecte avec l'authentification HTTP Basic et utilise trois points de terminaison — JSON-RPC, SSE et téléchargement de fichiers. Aucun framework et aucune bibliothèque JavaScript.

Téléchargez l'exemple terminé et suivez le guide : setup.sql (base de données) et index.html (page web).

1. Prérequis

  • Un serveur PostgreSQL en cours d'exécution et le binaire pgarachne (voir Installation).
  • Un navigateur moderne. Tout ce qui suit fonctionne avec le fetch() intégré — rien à télécharger.

2. Préparer la base de données

PgArachne se connecte lui-même avec un rôle de service et charge son schéma auxiliaire. Créez les deux une seule fois :

createdb my_database
psql -d my_database -c "CREATE ROLE pgarachne LOGIN PASSWORD 'pgarachne_password'"
psql -d my_database -f sql/schema.sql       # PgArachne helper schema (from the repository)
psql -d my_database -f setup.sql            # the demo role and functions (download above)

setup.sql crée un rôle de connexion webuser (la personne qui utilise la page web), un schéma api et trois fonctions. Le fonctionnement de chacune est expliqué aux étapes 5–7.

Les permissions constituent tout le modèle de sécurité. Un utilisateur ne peut appeler une fonction que si PostgreSQL l'y autorise : USAGE sur le schéma et EXECUTE sur la fonction. Dans la démo, webuser reçoit exactement ces droits sur trois fonctions — rien d'autre n'est accessible. PostgreSQL accorde par défaut EXECUTE sur les nouvelles fonctions à tout le monde ; pour de vrais projets, exécutez ALTER DEFAULT PRIVILEGES REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC et placez les fonctions exposées dans un schéma dédié (voir Sécurité & Authentification).

3. Configurer et démarrer PgArachne

Créez pgarachne.env à côté du binaire. STATIC_FILES_PATH permet à PgArachne de servir aussi la page web, de sorte que la page et l'API partagent la même origine (aucune configuration CORS nécessaire) :

DB_HOST=localhost
DB_PORT=5432
DB_USER=pgarachne
DB_SSLMODE=disable                 # local, non-TLS PostgreSQL only
STATIC_FILES_PATH=/path/to/folder/with/index.html

Le mot de passe du rôle de service est lu par le pilote PostgreSQL depuis PGPASSWORD (ou ~/.pgpass). JWT_SECRET n'est pas nécessaire — ce tutoriel utilise uniquement l'authentification Basic.

PGPASSWORD=pgarachne_password ./pgarachne

Ouvrez http://localhost:8080/ après avoir enregistré index.html dans ce dossier (étape 8). Le rôle webuser doit être autorisé à se connecter à PostgreSQL depuis l'hôte PgArachne (pg_hba.conf avec authentification par mot de passe).

4. Authentification : HTTP Basic

Le navigateur envoie l'utilisateur et le mot de passe PostgreSQL à chaque requête ; PgArachne ouvre une connexion en tant que cet utilisateur, de sorte que toutes les permissions PostgreSQL (et la Row-Level Security) s'appliquent directement.

// Authorization header. TextEncoder makes non-ASCII passwords work.
function authHeader(user, pass) {
  const bytes = new TextEncoder().encode(user + ":" + pass);
  return "Basic " + btoa(String.fromCharCode(...bytes));
}
const base = location.origin + "/db/my_database";   // /{API_PREFIX}/{database}

De mauvais identifiants renvoient HTTP 401 avec une erreur JSON ; les échecs répétés sont soumis à une limitation de débit (429).

5. Point de terminaison 1 — JSON-RPC : appeler une fonction

POST /db/{database}/jsonrpc appelle schema.function(jsonb). La fonction prend un seul argument jsonb et renvoie du json.

PostgreSQL (dans setup.sql) :

CREATE FUNCTION api.greet(params jsonb DEFAULT '{}'::jsonb) RETURNS json
LANGUAGE sql AS $$
  SELECT json_build_object(
    'message', 'Hello, ' || COALESCE(params->>'name', 'world') || '!',
    'database_user', current_user,
    'server_time', now());
$$;
GRANT USAGE ON SCHEMA api TO webuser;
GRANT EXECUTE ON FUNCTION api.greet(jsonb) TO webuser;

Navigateur :

async function rpc(method, params) {
  const res = await fetch(base + "/jsonrpc", {
    method: "POST",
    headers: { "Authorization": authHeader(user, pass), "Content-Type": "application/json" },
    body: JSON.stringify({ jsonrpc: "2.0", method, params, id: 1 }),
  });
  const body = await res.json();
  if (!res.ok || body.error) throw new Error(body.error.message);
  return body.result;
}

console.log(await rpc("api.greet", { name: "Alice" }));
// { message: "Hello, Alice!", database_user: "webuser", server_time: "..." }

Test avec curl :

curl -u webuser:webuser_password -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","method":"api.greet","params":{"name":"Alice"},"id":1}' \
  http://localhost:8080/db/my_database/jsonrpc

6. Point de terminaison 2 — SSE : recevoir des messages en temps réel

GET /db/{database}/sse?channels=demo diffuse les messages PostgreSQL NOTIFY sous forme de Server-Sent Events. N'importe quelle fonction peut publier avec pg_notify.

PostgreSQL :

CREATE FUNCTION api.send_message(params jsonb DEFAULT '{}'::jsonb) RETURNS json
LANGUAGE plpgsql AS $$
BEGIN
  PERFORM pg_notify('demo', json_build_object('from', current_user, 'text', params->>'text')::text);
  RETURN '{"sent": true}'::json;
END; $$;
GRANT EXECUTE ON FUNCTION api.send_message(jsonb) TO webuser;

Navigateur. L'EventSource intégré ne peut pas envoyer d'en-tête Authorization, lisez donc le flux avec fetch() :

async function listen(channels, onMessage, signal) {
  const res = await fetch(base + "/sse?channels=" + encodeURIComponent(channels), {
    headers: { "Authorization": authHeader(user, pass) }, signal,
  });
  if (!res.ok) throw new Error((await res.json()).error);
  const reader = res.body.getReader(), decoder = new TextDecoder();
  let buffer = "";
  for (;;) {
    const { done, value } = await reader.read();
    if (done) break;
    buffer += decoder.decode(value, { stream: true });
    let end;
    while ((end = buffer.indexOf("\n\n")) >= 0) {      // an event ends with a blank line
      const event = buffer.slice(0, end);
      buffer = buffer.slice(end + 2);
      for (const line of event.split("\n"))
        if (line.startsWith("data: ")) onMessage(JSON.parse(line.slice(6)));  // ":" lines are heartbeats
    }
  }
}

const controller = new AbortController();           // controller.abort() stops listening
listen("demo", (m) => console.log(m), controller.signal);
await rpc("api.send_message", { text: "Hello" });   // → { channel: "demo", data: { from: "webuser", text: "Hello" } }
Les canaux ne sont pas limités par rôle : tout utilisateur authentifié peut s'abonner à n'importe quel nom de canal. N'envoyez pas par NOTIFY des données que tous les utilisateurs ne peuvent pas voir (détails dans Notifications temps réel (SSE)).

Test avec curl : curl -N -u webuser:webuser_password "http://localhost:8080/db/my_database/sse?channels=demo", puis appelez api.send_message depuis un autre terminal.

7. Point de terminaison 3 — Fichier : télécharger un fichier généré

POST /db/{database}/file renvoie des octets bruts (ou un ZIP lorsque la fonction renvoie plusieurs fichiers) — sans base64 dans du JSON. La fonction renvoie des lignes (path, content, mime_type, store_only).

PostgreSQL :

CREATE FUNCTION api.export_report(params jsonb DEFAULT '{}'::jsonb)
RETURNS TABLE (path text, content bytea, mime_type text, store_only boolean)
LANGUAGE sql AS $$
  SELECT 'report.csv', convert_to('id,name' || E'\n' || '1,Alice' || E'\n' || '2,Bob' || E'\n', 'UTF8'),
         'text/csv', false;
$$;
GRANT EXECUTE ON FUNCTION api.export_report(jsonb) TO webuser;

Renvoyez plus de lignes pour obtenir automatiquement un ZIP. Voir Téléchargement de fichiers (/file) pour toutes les options.

Navigateur :

const res = await fetch(base + "/file", {
  method: "POST",
  headers: { "Authorization": authHeader(user, pass), "Content-Type": "application/json" },
  body: JSON.stringify({ method: "api.export_report", params: {}, options: { filename: "report.csv" } }),
});
if (!res.ok) throw new Error((await res.json()).error.message);   // errors are JSON, never binary
const url = URL.createObjectURL(await res.blob());
const a = Object.assign(document.createElement("a"), { href: url, download: "report.csv" });
document.body.appendChild(a); a.click(); a.remove();
URL.revokeObjectURL(url);

Test avec curl :

curl -u webuser:webuser_password -H "Content-Type: application/json" \
  -d '{"method":"api.export_report"}' http://localhost:8080/db/my_database/file -OJ

8. Assembler le tout

Enregistrez index.html dans le dossier STATIC_FILES_PATH et ouvrez http://localhost:8080/. Il contient les trois extraits ci-dessus reliés à des boutons (~100 lignes, aucune dépendance). Saisissez le nom de la base de données, conservez webuser / webuser_password et essayez chaque bouton : Call api.greet, Start listening puis Send, et Download report.csv.

9. Passer en production

  • HTTPS : les identifiants Basic circulent à chaque requête — utilisez toujours TLS (voir Déploiement & HTTPS) et changez le mot de passe de démonstration.
  • Conservez les identifiants uniquement en mémoire (une variable), pas dans localStorage. Pour des sessions sans renvoi du mot de passe, activez JWT_SECRET et utilisez get_jwt (voir Sécurité & Authentification).
  • Origine différente pour la page web (p. ex. un CDN ou un autre port) : définissez ALLOWED_ORIGINS=https://app.example.com. Les requêtes cross-origin sont bloquées par défaut.
  • Moindre privilège : un rôle PostgreSQL par type d'utilisateur, EXECUTE uniquement sur les fonctions nécessaires, Row-Level Security pour les données propres à chaque utilisateur.
